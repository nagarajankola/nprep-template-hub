Scope & definitions

What this covers

  • In scope: install / first launch → splash → authentication → the two intent branches → deferred profile collection → handoff onto the home page.
  • Out of scope: any post-onboarding product surface, the username/profile system, paid conversion / payment, and the personalised 3-day study plan (separate spec).

Key terms

TermDefinition
Known intentUser arrived pointed at a specific piece of content (a lecture / test) via a deep link or content-specific campaign. We take them straight to it.
Unknown intentUser arrived with no specific content target (organic install, direct open). They run the generic value-prop + first-lesson taste flow.
Truecaller loginOne-tap auth returning a verified name + phone. When available, it replaces manual entry and OTP.
Deferred promptA profile question not asked during onboarding — it surfaces later as a contextual prompt on the home page (e.g. grade).
HandoffThe moment the user lands on the home page. End of this spec's scope.

Intent detection & routing

Evaluated once, on first launch, before the first screen after splash renders. It decides the entire downstream branch.

✅
Rule — a user is Known intent if EITHER:
  • the launch carries a deep link with a resolvable content_id (WhatsApp / share / ad link to a specific lecture or test), OR
  • the install/launch carries a content-specific campaign tag that maps to a content item.
Otherwise → Unknown intent (organic / direct open).

Resolution order

OrderBehaviour
1 · Deep-link content_idKnown. Resolve content → load preview card (#5). Wins over campaign if both present.
2 · Campaign tag → contentKnown. Resolve campaign → content mapping.
3 · NeitherUnknown → Flow A (#4).
⚠️
Dangling content: if a deep link / campaign references content that no longer exists or fails to resolve, fall back to Unknown intent. Never block on a broken link.

Edge cases

ScenarioBehaviour
Both deep link AND campaign presentDeep-link content_id wins (more specific). Still Known.
Deep link to paywalled content (free user)Verify first, then GO PRO intercept at content open (#5).
Existing user opens a Known deep linkAuth resolves to login (#7) → straight into content; onboarding skipped.
Attribution SDK slow/unavailableDon't block splash; if no content_id deep link, default to Unknown.

Authentication

Phone is the identity key for both branches. Truecaller, when available, is sufficient on its own — no OTP.

Path A Truecaller — instant verify

✅
No OTP. A successful Truecaller verification authenticates immediately — the OTP screen is never shown on this path.
  • Returns phone + name in one tap.
  • Both persisted with phone_source = truecaller and name_source = truecaller.
⚠️
Mandatory tagging. The truecaller tags are load-bearing — they tell #6 the name is already captured (so the name step is skipped) and feed analytics.

Edge cases

ScenarioBehaviour
Not installed / declined / sheet dismissedFall through to Path B.
Token fails server validationSilently fall back to Path B.
TC name blankKeep verified phone; treat name missing → name captured per #6.
TC number is an existing accountTreated as login (#7).

Path B Manual number + OTP

✅
4-digit OTP. SMS auto-read where the OS permits; otherwise manual entry. phone_source = manual.
  • +91 default; once 10 valid digits are present, "Get OTP" auto-fires (details below).
  • Name (manual): collected at the number-entry step for Unknown; collected after OTP for Known (#6).

Edge cases

ScenarioBehaviour
OTP never arrivesWhatsApp → resend → edit number.
Wrong OTP repeatedlyInline error; rate-limit / backoff.
Number is existing accountVerifies → login (#7).
Drop mid-OTP (not verified)No account → next launch restarts (#8).

Phone number entry — detailed behaviour

  • Keyboard auto-opens on landing — the field is auto-focused; the user can type immediately.
  • Paste / autofill normalisation — whatever format the number arrives in, only the clean 10 digits are kept:
    • Pasted +91XXXXXXXXXX → strip +91 (shown as a fixed +91 prefix + 10 digits).
    • Pasted 0XXXXXXXXXX → strip the leading 0, keep 10 digits.
    • Spaces, dashes and brackets stripped; only the final 10 digits remain.
  • Auto-submit: on a fresh, from-scratch 10-digit entry, "Get OTP" fires automatically → OTP screen. If the user edits a returned / pre-filled number, Get OTP is tapped manually (no auto-fire).
  • Clear / edit: an X on the right of the number bar clears the whole field; tapping anywhere in the number edits it inline.

OTP verification — detailed behaviour

✅
4-digit OTP. Android: request SMS auto-read on landing — asked once; if denied, never asked again → manual. iOS: no SMS auto-read (not possible) — manual entry; the OS keyboard may suggest the OTP.
StateBehaviour
Android · permission allowedOTP auto-read → Verify auto-clicked → next screen.
Manual (iOS, or Android denied)On a fresh, full 4-digit entry, Verify is auto-clicked.
No OTP after 30sResend appears — OTP via SMS or OTP on WhatsApp (tap to switch). On Android with permission, the resent OTP auto-reads too.
Invalid OTPRed error state. The user can tap any single digit box and fix just that digit. After a single-digit edit, Verify is not auto-clicked — the user taps Verify (auto-click only on a fresh full entry).
Edit number"Edit" returns to the phone screen with the number pre-filled (X to clear, or tap to edit inline).
On successA brief success toast → name step (Known) / subject (Unknown).
🔑
Identity = phone. The account is keyed on the verified number. A user is "existing" the moment a verified phone matches a prior record (#7).

Interactive lesson — checkpoint mechanics

🎬
Attempt-anytime, checkpoint-gated. The video carries 3 checkpoints tied to 3 questions. Questions are attemptable throughout; the video only pauses if a checkpoint is reached unanswered.
  • Landing state: the "answer 3 questions" bar is highlighted (animated) and the video is highlighted. The video auto-starts. Questions are visible and attemptable throughout — not locked.
  • While playing: the user can answer the current question at any time; submitting lets the video keep playing. Not answering is not treated as "not attempted".
  • At a checkpoint: if that segment's question hasn't been answered correctly yet, the video pauses there until it is.
  • Correct answer → video continues to the next segment / checkpoint.
  • Wrong answer → re-attempt allowed (no limit); at a checkpoint the video stays paused until the answer is correct.
  • All 3 correct → the next screen unlocks.
  • Score = number correct on the first attempt (0–3); this is what the score screen reflects, so its variants stay meaningful even though finishing requires all 3 eventually correct.

Profile data collection

Name is captured inline at a defined low-friction point. Grade is the only deferred question — never asked during onboarding; it pops when the user enters a feature that needs grade to personalise.

Name inline

✅
If Truecaller supplied it, never ask. Otherwise capture at the defined point per branch.
Source / intentWhen captured
Truecaller (either)Already have it. Never asked.
Manual · UnknownAt the number-entry step (#3).
Manual · KnownRight after OTP, before the content (#5).

Input rules

  • Letters only — any script (Unicode letters, incl. Hindi / regional), plus spaces and . ' -; no emoji, numbers or other symbols; no leading space.
  • Auto-capitalise the first letter of each word by default. This is a soft default — if the user manually changes a letter to lower/upper case, their choice is kept.
  • Length: min 2, max 35 characters.
⚠️
Not skippable. If the user closes the app before entering it, the name is asked again the next time they open the app (#8).

Grade deferred / blocking

✅
Always deferred, both flows. Never an onboarding screen.
  • Grade = program → year.
  • Trigger: the user enters a feature that needs the grade data point to personalise (e.g. QBank, Tests). Exact feature set decided by engineering.
  • Behaviour: Blocking — must answer to enter that feature. Asked once; then never again.

Edge cases

ScenarioBehaviour
Grade prompt dismissed / backed outBlocking — the feature does not open. Re-prompt on the next attempt.
Name closed before entryRe-asked next launch (not skippable).
Truecaller name blankTreated as missing → captured per the branch rule.
Existing user missing gradeSame grade gate applies after login (#7).
7

Existing / returning users

✅
Match = login. On verify (Truecaller or OTP), if the phone matches an existing account → log straight in → home page. A live session at launch bypasses auth entirely.
  • Missing name → name asked (#6); missing grade → grade gate when entering a feature that needs it.
  • Existing users still pass through the value banners — because the phone step comes after the banners — but they skip the subject screen and the taste quiz.
  • Existing user via a Known deep link → straight into the deep-linked content after login.

Edge cases

ScenarioBehaviour
Existing user, full profileHome page, no prompts (Known link → straight to content).
Existing user, missing name + gradeHome page → name asked → grade when entering a feature that needs it.
Same phone, new deviceVerify → matches → restore profile; no re-onboarding.
Account from incomplete onboardingHandled by resume rules (#8).
Session expiredRe-verify (#3) → match → login.

Drop-off & resume logic

The dividing line is phone verification. Before it, no account → restart. After it, the user is recoverable.

Where they droppedAccount stateNext launch
Before verification
(splash, banners, phone, mid-OTP)		No verified phone → no accountRestart from the top of the flow; re-evaluate intent (#2).
After verify, name pendingAccount (phone); name missingAuto-login → name asked again → then home page; grade on interaction.
Name done, profile incompleteAccount + nameAuto-login → home page; grade on interaction. Any unfinished Unknown steps (subject, taste) are not resumed.
Fully onboardedCompleteAuto-login → home page, no prompts.
🧭
An onboarding_state field (verified → named → complete) is the source of truth for resume routing.

Edge cases

ScenarioBehaviour
Drop pre-OTP, returns days laterNo account → fresh start; intent re-evaluated (a new deep link could change the branch).
Drop post-verify on Known, returns via the same deep linkAuto-login → name (if pending) → restore the content they came for.
Drop post-verify on Known, cold open or different linkAuto-login → name (if pending) → home page (content not restored).
Unknown user drops after name, before subject/tasteAuto-login → home page; subject and taste are not collected/run for that user.
App killed by OS mid-flowSame matrix, keyed on onboarding_state.
Verified but profile write failedRe-attempt write next launch; treat as earliest pending state until confirmed.
